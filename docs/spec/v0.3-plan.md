# disdetta v0.3 specification: catalog and `plan`

Status: draft (2026-10-14). Extends v0.1 and v0.2. First end-to-end target: Bitnami `postgresql` -> CloudNativePG (PLAN.md decision 3).

## 1. Catalog (data, embedded)

`catalog/routes/<chart>.yaml`, one file per Bitnami chart, validated against `schemas/catalog-v1.json` in tests:

```yaml
schemaVersion: "1"
chart: postgresql
appliesTo: ">=15.0.0 <17.0.0"        # Bitnami chart versions (semver range)
maturity: verified | partial | route-only
routes:
  - id: cloudnative-pg
    target: {name: CloudNativePG, kind: Cluster, apiVersion: postgresql.cnpg.io/v1, version: "1.27"}
    recommended: true
    migration: side-by-side          # in-place is never claimed
    source: {url: https://cloudnative-pg.io/docs/..., verified: 2026-10-14}
mappings:                            # only for routes with maturity verified/partial
  - from: primary.persistence.size
    to: spec.storage.size
    kind: rename                     # rename | constant | transform | manual | unmapped
    source: {url: ..., verified: 2026-10-14}
    note: "Size cannot be decreased."
checklist:
  - id: stop-writes
    text: "Stop writes on the source before the final import; later changes are not copied."
    source: {url: ...}
```

Rules:
- Every route, mapping and checklist line has `source.url`; mappings also `source.verified` (date). Missing source fails the schema test.
- `transform` names a registered pure function (`split-lines`, `parse-postgresql-conf`, `instances-from-architecture`, `split-comma`), each with table tests.
- `manual` and `unmapped` carry a `note` explaining why. They are emitted in the unmapped list, never in the generated values.
- Charts without verified mappings ship as `route-only`: `plan` prints the route and checklist, no values.

## 2. `disdetta plan`

```
disdetta plan --release NAME (--from-repo PATH | --from-cluster [--context ...] [--namespace NS] --read-helm-secrets)
              [--route ID] [--out DIR] [--format table|json]
```

- Input values: from the repo (the HelmRelease / Argo Application / values files referencing the release; when several values files apply, the user passes `--values FILE ...` in Helm order) or from the cluster (tier 3 `config`, which requires `--read-helm-secrets`). Chart name and version come from the same source; an unknown chart version outside every `appliesTo` range is an error (exit 2), never a guess.
- Output (to `--out`, default stdout as a multi-document stream):
  - `target.yaml`: the destination resource(s) built only from `rename`/`constant`/`transform` mappings of keys the user actually set, plus required fields with documented defaults from the catalog;
  - `unmapped`: every user-set key not translated, with kind (`manual`, `unmapped`, `unknown` for keys absent from the catalog) and note;
  - `checklist.md`: route checklist, ordered, with sources, plus generated items (for example one per `manual` key);
  - a coverage line: `mapped N of M user-set keys`.
- Secrets: values of keys under `auth.*`, `*password*`, `*token*`, `*secret*` and any value from a Kubernetes Secret are never copied into `target.yaml`; the mapping emits a reference to a Secret the user must create, and a checklist item.
- Deterministic; nothing is applied; read-only as `scan`.

## 3. Exit codes

0 plan generated with every user-set key mapped; 4 plan generated with unmapped or manual keys (not an error, a signal for CI); 2 usage or input error (release not found, chart version not covered). 

## 4. Acceptance
- Golden plan per fixture (`testdata/plan/postgresql/{standalone,replication,custom-conf,existing-secret}`), table and JSON.
- Schema test for every catalog file; a test that every mapping `source.url` is https and every `transform` is registered.
- A test that no planted secret value from the input values appears in any output file.
- Mappings for PostgreSQL ship only after issue #2 (verification) is closed; until then the catalog entry is `partial` and only rows marked verified are applied.
