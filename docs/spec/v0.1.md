# disdetta v0.1.0 specification

Status: accepted (2026-10-14). This is the contract for the first release. Anything not listed here is out of scope for v0.1.0.

## 1. Scope

v0.1.0 ships `disdetta scan [path]` for repositories only. Cluster scan (`--cluster`) and `plan` are later releases (see [PLAN.md](../PLAN.md)).

Out of scope: cluster access, template rendering, network access of any kind, SARIF, fixing files.

## 2. Finding model

A finding is a Bitnami dependency found in configuration. A diagnostic is a problem of the scan itself (a file that could not be read or parsed). They are separate lists and never mixed.

```go
type Finding struct {
    RuleID      string        // stable, e.g. "DSD-IMG-001"
    Severity    Severity      // high | medium | low
    Confidence  Confidence    // confirmed | inferred | unresolved
    Impact      Impact        // high | medium | low | unknown (migration impact)
    Component   string        // e.g. "postgresql"; "" when unknown
    Location    Location      // path (slash-separated, relative to the scan root), line, column (1-based)
    Reference   string        // normalized reference, redacted per section 6
    Original    string        // the reference as written, redacted per section 6
    Attributes  []string      // sorted subset of: mirror, pull-risk, chart, embedded-values
    Fingerprint string        // section 5
}
```

### 2.1 Rules

| Rule | Severity | Meaning |
| --- | --- | --- |
| `DSD-CFG-001` | high | `allowInsecureImages: true` (YAML bool, any case) under `global.security` at any depth: top level, or under a subchart key (`keycloak.global.security...`), as seen in the corpus. The Bitnami image guard is switched off. |
| `DSD-IMG-001` | high | Image under `bitnamilegacy/`: frozen, no security updates. |
| `DSD-IMG-002` | high | Image under `bitnami/` with a version tag or digest (anything but `latest` or no tag). Attribute `pull-risk`: versioned tags left the public path on 2025-08-28; a pull may fail, a cached copy is unpatched. |
| `DSD-IMG-003` | medium | Image under `bitnami/` with `latest` or no tag, or under `bitnamisecure/` with any tag: community tier, intended for development only. |
| `DSD-IMG-004` | low | Image under `bitnami/` or `bitnamisecure/` in a registry other than Docker Hub (the Bitnami namespace appears as any path segment, e.g. `ghcr.io/acme/bitnami/redis`). Either a mirror (frozen unless refreshed) or a rebuild from the Bitnami sources, which is a recommended exit. Attribute `mirror`, confidence `inferred`. `bitnamilegacy/` under another registry stays `DSD-IMG-001` (a copy of frozen content). |
| `DSD-CHT-002` | medium | Bitnami chart vendored in the repository: a `Chart.yaml` whose `sources` or `home` point to `github.com/bitnami/charts`, or whose `annotations.images` list Bitnami images. One finding per vendored chart, attribute `chart`, impact from the chart name. |
| `DSD-CHT-001` | medium | Chart sourced from Bitnami: `https://charts.bitnami.com/bitnami`, `oci://registry-1.docker.io/bitnamicharts`, `oci://docker.io/bitnamicharts` (also Flux `HelmRepository.spec.url`, Argo `repoURL`, Kustomize `helmCharts[].repo` and `HelmChartInflationGenerator.repo`). Attribute `chart`. |

Source for all rules: https://github.com/bitnami/charts/issues/35164 and `bitnami/common/templates/_errors.tpl` (see research notes sections 1-2).

Excluded on purpose (not findings): `bitnami/sealed-secrets*`, `bitnami/minideb`, `bitnami/charts-syncer` images still published on `docker.io/bitnami` (same source, "unaffected projects"). VERIFY: exact image names of those projects.

### 2.2 Confidence

- `confirmed`: the full reference is literal and its namespace is on `docker.io` (any Docker Hub alias, or implicit).
- `inferred`: Bitnami namespace under another registry (a mirror or a rebuild; see `DSD-IMG-004`), or an image found as a whole scalar under a key that is not a known image key (section 9). Attribute `mirror` when the registry is not Docker Hub.
- `unresolved`: part of the reference is templated (`{{ }}` or `${ }`/`$VAR`) but the static part identifies a Bitnami namespace (e.g. `bitnami/redis:{{ .Values.tag }}`). The rule is chosen from the static part; when the tag is templated, `DSD-IMG-002` applies (assume versioned, the common case) and the finding says so via confidence.

A reference with no static Bitnami evidence (`{{ .Values.image }}`) is not a finding: it is listed as diagnostic `DSD-SCN-003` (level info). `summary.unresolved` is the number of `DSD-SCN-003` diagnostics only; findings with confidence `unresolved` are not counted there.

### 2.3 Migration impact

From an embedded component table (data file `internal/catalog/components.yaml`, one entry per Bitnami repository name, with `impact` and `component`):
- `high`: stateful data stores and identity: postgresql, postgresql-repmgr, redis, redis-cluster, redis-sentinel, valkey, valkey-cluster, kafka, mongodb, mongodb-sharded, keycloak, mariadb, mariadb-galera, mysql, rabbitmq, elasticsearch, opensearch, cassandra, zookeeper, etcd, minio, clickhouse, influxdb.
- `low`: helpers that are replaced without data: os-shell, bitnami-shell, kubectl, git, nginx, *-exporter.
- `medium`: any other Bitnami application image.
- `unknown`: chart findings without a resolvable chart name, and `DSD-CFG-001`.
Chart findings take the impact of the chart name (dependency `name`, HelmRelease `chart`, Argo `chart`) when present.

## 3. Diagnostics

| Code | Level | Meaning |
| --- | --- | --- |
| `DSD-SCN-001` | error | Malformed file (YAML or embedded values). |
| `DSD-SCN-002` | warning | File skipped: symlink or non-regular file. Every skip counts in `summary.filesSkipped`. |
| `DSD-SCN-008` | error | File larger than the size limit (16 MiB) not scanned: it may hold findings, so the scan is incomplete. Counts in `summary.filesSkipped`. |
| `DSD-SCN-003` | info | Unresolved reference without Bitnami evidence. |
| `DSD-SCN-004` | error | Read error. |
| `DSD-SCN-005` | warning | Limit reached: YAML depth (256), Dockerfile line length, HCL depth (256) or Terraform node budget (100000). |
| `DSD-SCN-006` | warning | Ignore entry expired. |
| `DSD-SCN-007` | info | File read as template text (Helm `templates/`, `*.tpl`, or YAML with `{{` that does not parse): scanned line by line, see section 9.1. Not an error: the scan stays complete. |

Every code has a page in `docs/diagnostics/` (rules too). Old codes `DSD-001..006` are removed (never released).

## 4. Ordering

Findings: severity (high, medium, low), impact (high, medium, low, unknown), path, line, column, rule. Diagnostics: path, line, code. No map iteration in output.

## 5. Fingerprint

`hex(sha256(ruleID + "\x00" + path + "\x00" + reference + "\x00" + occurrence))[:16]`, where `occurrence` is the 0-based index among findings with the same rule, path and reference in source order (line, then column), independent of detector iteration order. An anchor and its alias uses are one logical reference, reported once at the anchor. Line numbers are excluded so a fingerprint survives unrelated edits. Used by ignore files (v0.1.0 milestone M1b).

## 6. Redaction

- Never print a YAML value other than the reference itself; never print anything under a Kubernetes `Secret`, at any depth (a `Secret` inside a `List` or any `items` array included).
- Diagnostics paths are relative to the scan root; a config file outside the root is reported by base name only.
- Table cells escape control characters and Unicode format characters (category Cf, e.g. U+202E, U+200B).
- References with userinfo (`user:pass@host`) are dropped to `registry/repository`.
- Unresolved references print the static part and `{{…}}` for each templated segment, never the template body.
- Table cells escape control characters.

## 7. CLI

```
disdetta scan [path] [--format table|json] [--fail-on high|medium|low|none] [--rule ID ...] [--exclude GLOB ...] [--config FILE]
```

- `--fail-on` default `low` (any finding fails). `none` never fails the policy.
- `--rule` filters findings (repeatable); diagnostics are not filtered.
- `--exclude` skips paths matching a slash-separated glob relative to the root (repeatable, `**` supported); excluded files are not counted as scanned or skipped.
- stdout: the report only. stderr: errors and logs.

### Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Scan complete, no finding at or above `--fail-on`. |
| 1 | Policy failed: at least one finding at or above `--fail-on`. |
| 2 | Usage error or fatal error (root missing, unreadable root). |
| 3 | Policy passed but the scan is incomplete (at least one error-level diagnostic). |

1 wins over 3. An incomplete scan never exits 0.

## 8. Output

Table: one row per finding (`LOCATION RULE SEVERITY CONFIDENCE IMPACT REFERENCE`), then diagnostics of level warning and error, then one summary line:
`scanned 142 files, skipped 1, findings 8 (high 5, medium 2, low 1), diagnostics 2, unresolved 2`.

JSON (`schemaVersion: "1"`, schema in `schemas/report-v1.json`, validated in tests):
```json
{
  "schemaVersion": "1",
  "tool": {"name": "disdetta", "version": "dev"},
  "summary": {"filesScanned": 0, "filesSkipped": 0, "findings": {"high": 0, "medium": 0, "low": 0}, "diagnostics": 0, "unresolved": 0, "complete": true},
  "findings": [],
  "diagnostics": []
}
```
Field names are stable; new fields may be added in a minor release, never removed or renamed within schemaVersion 1.

## 9. Sources scanned (v0.1.0)

values files (any `*.yaml`/`*.yml`), `Chart.yaml` dependencies, plain Kubernetes manifests (all pod spec containers), Flux `HelmRepository`, `OCIRepository`, `HelmRelease` (`spec.values`), Argo CD `Application`/`ApplicationSet` (`repoURL`, `chart`, `helm.values`, `helm.valuesObject`), Kustomize `images[].newName` plus each `helmCharts[]` entry's Bitnami `repo` and `valuesInline` images, the `valuesFile` of a `helmCharts` entry and of a `HelmChartInflationGenerator` (section 9.2), docker-compose `image`, GitHub Actions (`container`, `services`, `uses: docker://`), GitLab CI (`image`, `services`, both string and `name:` forms), Azure Pipelines (`container`, `resources.containers[].image`), Dockerfile (`FROM`, `COPY --from`, `ARG` defaults, line continuations), Helmfile (`helmfile.yaml`, `helmfile.yml`, `helmfile.d/*.yaml`, `*.yaml.gotmpl`). YAML aliases and merge keys are resolved with a cycle guard. Image triples are recognized wherever a mapping has a `repository` whose value is image-shaped (not only under a key named `image`: e.g. `sysctlImage`, `volumePermissions.image`), joined with sibling `registry`, `tag`, `digest`.

Helmfile repositories resolve chart aliases and inline values maps, while gotmpl files are handled as template text. The repositories and the releases of a Helmfile file are resolved together whatever their order: a release resolves against the repositories declared in any document of the same file (`---` separated documents included). One dependency is one finding: a release that uses the Bitnami chart repository is reported on its `chart:` entry and the repository URL is not reported a second time, while a repository that no release uses is reported on its `url:` entry. A repository name declared more than once is the Bitnami repository when any of its declarations is. A templated `chart:`, `version:` or `values:` entry names no repository alias, and a templated repository URL is never certain: neither is a finding.

A release may also name the Bitnami OCI chart repository directly, without a repository alias: `chart: oci://registry-1.docker.io/bitnamicharts/<chart>` (or `oci://docker.io/bitnamicharts/<chart>`) is reported on its `chart:` entry, with the component of the last path segment of the reference. A templated chart reference keeps the static reference but is never certain: it is reported with confidence `unresolved` and no component.

A repository that no release uses is reported when it is the Bitnami chart repository, in the `https://charts.bitnami.com/bitnami` form and in both OCI forms (`oci://registry-1.docker.io/bitnamicharts`, and the bare `registry-1.docker.io/bitnamicharts` with `oci: true`).

A gotmpl Helmfile is read line by line: a `repositories:` or `releases:` section holds its list entries whatever the column they are written at, and a template action line (`{{ ... }}`) never ends the section. A `chart:` key is the chart of a release only at the property indent of the release entry, so a key nested in the values of a release is never the chart of the release. A Go template comment (`{{/* ... */}}`) is ignored: from the line that opens the comment to the line that closes it, the lines are not read as YAML, so a commented-out repository or release is never a finding.

Known limitation: Helmfile layers and bases are not followed. `helmfiles:` and `bases:` includes are not read, so a repository alias that is declared in another file is unknown in the file that uses it and the release is not reported.

Known limitation of a gotmpl Helmfile: the file is read line by line, not as YAML. A flow-style entry (`- {name: bitnami, url: https://charts.bitnami.com/bitnami}` written on one line inside a list) is not read, so its repository and its releases are unknown; and a template action line with a trailing comment (`{{ if .Values.extra }} # optional`) is not a template action line any more, so it ends the section of the file and the entries that follow it are not read.

Terraform files (`*.tf`) are parsed, never evaluated: only literal expressions are read, so no function, variable, file or environment value is ever resolved. The `values` attribute is scanned as embedded YAML documents and as `yamlencode` objects, and the `set`, `set_list` and `set_sensitive` blocks as single values. A component that is not a literal (the tag, registry or digest of an image triple, the name of a chart) keeps only its static part: the finding is reported with confidence `unresolved` (section 2.2), and a reference without static Bitnami evidence stays a `DSD-SCN-003` diagnostic. Arguments of `file(...)` are ignored: the referenced file is scanned on its own as a repository file, never through the expression that names it. The HCL depth limit (256) and the node budget (100000) are reported as `DSD-SCN-005`. Known limitation: Terraform JSON configuration (`.tf.json`) is out of scope for v0.1.0 and is not scanned.

Whole-scalar fallback: any YAML scalar whose entire value is an image reference with a Bitnami namespace (e.g. `kubectl: bitnamilegacy/kubectl:latest`) is a finding with confidence `inferred`, even under an unknown key. Any YAML scalar that contains a Bitnami chart repository URL (section 2.1, `DSD-CHT-001`) is a chart finding, in any file (e.g. chart-testing `ct.yaml` `chart-repos`, custom dependency lists). Partial matches inside longer text (paths such as `/opt/bitnami/...`, prose, URLs to `github.com/bitnami`) are never findings.

### 9.2 Shell commands in CI scripts

CI files carry commands as strings (`script:`, `before_script:`, `after_script:`, `run:`, `steps[].script`, `bash:`, `powershell:`, `pwsh:`, Azure `script:`, Dockerfile `RUN`). Corpus finding (2026-10-15, 28 public repositories): `docker run bitnami/kubectl:1.17.4 ...` and `helm repo add bitnami https://charts.bitnami.com/bitnami` inside scripts were missed. Rule: in script strings, tokenize the command line (POSIX-like quoting, line continuations, `&&`/`;`/`|` separators, no shell evaluation, no variable expansion) and report:
- the first non-option argument that is an image reference with a Bitnami namespace after `docker|podman|nerdctl run|create|pull|exec|build --from` (options with values such as `-v SRC:DST`, `-e K=V`, `--name N` are skipped), and `--image bitnami/...` / `--image=bitnami/...` (`kubectl run`, `docker buildx`);
- `helm repo add <name> <url>` when `<url>` is a Bitnami chart source (DSD-CHT-001);
- `helm install|upgrade|template|pull <release> <alias>/<chart>` only when the same script block (or the same file) declared `helm repo add <alias> <Bitnami url>`; the finding carries the component from `<chart>`; and `helm ... oci://registry-1.docker.io/bitnamicharts/<chart>`;
- `--set image.repository=bitnamilegacy/...` / `--set global.security.allowInsecureImages=true` on `helm` command lines (DSD-IMG-001 / DSD-CFG-001).
Findings are `inferred` (a command line, not configuration), rule per the image, location = the line and the column of the token in the source file, the column counting the characters of the line (a folded block scalar reports the line of the token, not the first line of the folded text). A plain, single-quoted or double-quoted scalar has no position table, so all its tokens are reported on the first line of the scalar. Commented lines and `echo`/`printf` arguments are ignored. Negative cases: `docker run busybox echo bitnami/kubectl`, `docker build -t bitnami/mycustom .` (a tag being created, not a pulled image) and prose in comments. Redaction: only the reference is printed, never the rest of the command line.

Only the positions the CI system defines hold scripts: the `run` key of a step of a GitHub Actions job, the `script`, `before_script` and `after_script` keys of a GitLab CI job (a list of commands or a single command), and the `script`, `bash`, `powershell` and `pwsh` keys of an Azure Pipelines step, at the root, in a job or in a stage. A key with the same name anywhere else, such as a `with` input, is never a script. A YAML alias to a steps list or to a script is resolved before the keys are read. A script a job inherits through a merge key (`<<`) is the anchored script: it is reported once, at its anchor.

The value-taking options of `docker run`/`docker create` and of the `helm` commands are known: an option consumes the token that follows it, so the reference behind it is still found, and a boolean option never consumes a token. A `docker` option that is in neither table consumes a number, so an option the tables do not know yet does not hide the reference behind it.

The traversal of a CI file is bounded: a YAML anchor that references itself ends the traversal instead of overflowing the stack, and the scan of the file terminates.

Shell variables, aliases and functions are never resolved: a Bitnami reference that is only reachable through a variable is not reported by this detector, and only the references that are literally present are reported. The whole-scalar fallback (section 9) does not apply to script scalars: a script scalar without a tokenizer finding is not reported at all.

### 9.1 Template text

Helm templates are not YAML. Files under a chart's `templates/` directory, `*.tpl`, and YAML files that fail to parse and contain `{{` are scanned line by line instead of being reported as malformed:
- the scalar after an `image:` or `repository:` key (quoted or not) is classified with the template-aware reference parser (section 2.2);
- quoted string literals inside `{{ }}` that parse as an image reference with a Bitnami namespace (for example `default "bitnami/kubectl:latest"`) are findings with confidence `inferred`;
- comment lines (`#`, `{{/* */}}`) are ignored.
Each such file adds one `DSD-SCN-007` (info).

Corpus finding (2026-10-14): before this rule every `templates/` file was reported as malformed (exit 3 on every Helm chart repository) and image literals inside templates were missed (see `docs/corpus.md`).

### 9.2 Kustomize

A Kustomization file is `kustomization.yaml`, `kustomization.yml` or the extensionless `Kustomization`, matched case-insensitively. Its `images[]` entries and its `helmCharts[]` entries are scanned, whatever the name of the file.

A `HelmChartInflationGenerator` document is detected by its `kind`, in any file: its `repo`, its `valuesInline` and its `valuesFile` are scanned.

The `valuesFile` of a `helmCharts` entry is resolved relative to the directory of the Kustomization file that declares it, and the `valuesFile` of a `HelmChartInflationGenerator` relative to the directory of the generator file; the file is scanned as chart values, whatever its name: the whole file is scanned for image references, like a values file. Known difference: kustomize resolves the `valuesFile` of a generator relative to the kustomization root, not to the directory of the generator file.

The resolved path must stay inside the scan root. An absolute path, a path that escapes the root with `..`, and a path that reaches a symbolic link are refused; a symbolic link is never followed, so a values file is never read from outside the root. Every directory between the root and the file must be a plain directory (a symbolic link or a Windows junction is not), and the file must stay inside the root once every link is resolved. A refused, missing or unreadable reference is reported as `DSD-SCN-004` (read error) and leaves the scan incomplete; a file that is skipped is reported as `DSD-SCN-002`, never as a crash.

A values file that the walk finds as well is scanned once, as chart values: one reference is never reported twice.

## 10. Acceptance

- Every rule and every source in section 9 has positive and negative table tests citing their source.
- Goldens for table and JSON; JSON validated against `schemas/report-v1.json`.
- Fuzz targets: image reference parser, Dockerfile scanner, YAML walker.
- Security tests: no value from a `Secret`, no userinfo, no template body in any output.
- Corpus (M1c) recall ≥ 90% and precision ≥ 95% on the supported sources before the v0.1.0 tag. Determinism: two runs byte-identical.
- CI: build, vet, `test-race` on Linux, lint, govulncheck, coverage floor 80% on `imageref`, `detect`, `report`.
